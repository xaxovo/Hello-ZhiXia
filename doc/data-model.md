# 数据层契约

> **这份文档里的约定，全部属于「第一天就必须做对」的类别。**
>
> 它们决定了数据长什么样。推迟它们不会省下任何前期工作，只会让最后一公里变成三端同时重写数据层。

## 为什么需要一个共享数据层

三端各自实现会导致三个必然结果：

1. **三套数据模型** — 最后无法互相解析对方的数据
2. **冲突无法合并** — 各自直接改字段，无法表达「两端同时改了同一条」
3. **经验无法复用** — 一端踩过的坑，另两端必然重踩

因此三端**共用一个 TypeScript 数据层包**（暂定 `packages/core-sync`）。各端只实现自己的 UI 与平台适配。

---

## 一、标识符：ULID

**规则**：所有实体、操作、事件的主键一律使用 **ULID**。

| | |
| --- | --- |
| 格式 | 26 字符 Crockford Base32，48 位毫秒时间戳 + 80 位随机 |
| 为什么 | 前缀即时间 → 天然按创建顺序排序；无需中心分配；碰撞概率可忽略 |
| 禁止 | 数据库自增整数、以 UUIDv4 作排序键 |

**自增整数在无中心环境下必然撞车**，而且一旦撞车，修复要重写全部外键关系。

> 时间戳部分由墙钟生成，**只用于排序与调试，不可用于冲突判定**（见下一节）。

---

## 二、逻辑时钟：HLC（混合逻辑时钟）

所有操作携带一个 HLC 三元组：`(wallMillis, counter, deviceId)`。

**产生规则**

- 本机事件：`wall = max(localNow, lastWall)`；若 `wall == lastWall` 则 `counter++`，否则 `counter = 0`
- 收到远端事件：`wall = max(localNow, lastWall, remoteWall)`，然后按 **maxWall 由谁决定** 分四种情况取 counter：

  | 情况 | counter 取值 |
  | --- | --- |
  | 物理时钟领先 | `0` |
  | 本地 wall 最大，且与远端相同 | `max(本地 counter, 远端 counter) + 1` |
  | 仅本地 wall 最大 | 本地 counter + 1 |
  | 仅远端 wall 最大 | 远端 counter + 1 |

- 比较：先比 `wall`，相等比 `counter`，再相等比 `deviceId`（字典序）

> ⚠️ **不要把「收到远端事件」简化成「再执行一次本机规则」。** 那是错的：若本地 counter 是 1、远端是 5，简化写法会产出 `(wall, 2)` —— 比刚刚观察到的事件还早，因果序被破坏。
>
> 这个错误很容易写出来，也很容易在单机测试里漏掉（两台设备的 counter 恰好不冲突时看不出问题）。`core-sync` 里有一个专门的用例盯着它：`observe 产出严格大于远端的时间戳（本地 counter 落后于远端时的关键性质）`。

**为什么不用墙钟**：各设备时钟漂移不一致，仅靠墙钟会导致排序错乱、冲突判定错误。

**为什么不用纯 Lamport**：丢失「大致发生时刻」，无法做超时与缓存淘汰。

**墙钟的唯一用途**：界面展示、日志、超时判断。**冲突判定一律用 HLC。**

## 三、写入方式：只追加操作日志（op log）

**规则**：任何状态变更都表达为一个**不可变操作**，追加进日志；当前状态由日志折叠（fold）得出。

```
Op {
  opId:           ULID
  hlc:            { wall, counter, deviceId }
  entityId:       ULID
  type:           string          // 例如 "note.setTitle"
  payload:        JSON
  schemaVersion:  number
  causalContext?: Frontier        // 产生这条操作之前已知的同步前沿，见第十节
}
```

**禁止**：跨设备直接 `UPDATE` 字段。

> `causalContext` 是 2026-10-14 新增的字段（[ADR-0015](./decisions/0015-sync-frontier-and-compaction.md)）。
> 它回答的是「写这条操作之前，我知道些什么」—— **HLC 给的是全序，不是因果序**，
> 所以光有时间戳无法判定两条操作是否并发。字段可缺省（旧数据仍可解析），
> 但缺省的代价是并发性**不可判定**，冲突检测会把它如实报告出来，而不是静默当成「没有冲突」。

**快照**：定期把折叠结果存为快照，控制启动时间。**快照可随时丢弃并重建；操作日志不可丢弃。**

**为什么**：直接改字段是「状态覆盖」，无法表达两个并发的意图；操作日志是「意图追加」，可以被合并、重放、审计。

---

## 四、删除：墓碑（tombstone）

**规则**：删除 = 追加一个 tombstone 操作，**不是物理删除**。

**为什么必须**：如果直接物理删除，一台离线三个月的设备重连后，会把它本地那份「还没删」的数据同步回来，**已删除的数据就复活了**。

**保留策略**

| 项 | 约定 |
| --- | --- |
| 墓碑保留期 | **180 天**（[ADR-0014](./decisions/0014-deletion-semantics.md)），下限必须大于「设备可能离线的最长时间」 |
| 裁剪的前置条件 | **每台配对设备的前沿都必须覆盖该墓碑**（见第十节）。「保留期已过」**不能**替代这一条 |
| 彻底清除 | 属于分布式问题：需所有已知设备确认，或明确告知用户「最后一致」的语义 |
| 附件内容 | 内容寻址 → 无设备引用后才可回收 |

---

## 五、Schema 版本化

**规则**：每个实体带 `schemaVersion`；迁移是**纯函数** `vN → vN+1`。

- 迁移必须在**任意设备上独立执行且结果确定**
- 新设备必须能解析**任意历史版本**的数据
- 迁移函数一旦发布**不可修改**（否则不同设备上的迁移结果会分叉）

## 六、数据分类与同步策略

**这是让同步从困难变简单的关键一刀。** 很多人做同步失败，是因为试图同步一切。

| 类别 | 例子 | 策略 | 原因 |
| --- | --- | --- | --- |
| **可合并** | 笔记、日程、待办、会话、提醒条目 | 全量复制，op log 合并 | CRDT 天然支持并发合并 |
| **可重建（派生）** | 向量索引、摘要、全文索引、搜索结果缓存 | **不同步**，本地按原文重建 | 派生态可重建；同步它既昂贵又易出错 |
| **内容（二进制）** | 附件、图片、PDF、录音 | 内容寻址 + 按需拉取 + 离线标记 | 避免每台设备装下全部内容；天然去重 |

**「全量复制」的准确含义**：全量复制的只有第一类（结构化数据，通常几十 MB）。第二类本地重建。第三类按需。

> 派生态重建的唯一成本是 embedding 调用费用，因此**必须为其设上限**（见 [open-questions #10](./open-questions.md)）。

## 七、冲突解决规则

| 数据类型 | 规则 | 说明 |
| --- | --- | --- |
| 文本内容 | CRDT 自动合并（Yjs / Automerge） | 无需人工介入 |
| 集合成员 | OR-Set（增删并发时**增优先**） | 避免条目神秘消失 |
| 标量字段（标题、状态、标签） | LWW（Last-Writer-Wins），**判定用 HLC** | 简单且可预测 |
| 日程时间、金额、账号类 | LWW + **保留冲突副本** | 禁止静默丢弃，必须让人看见 |
| 不可自动合并的强冲突 | 标记为冲突，交人工处理 | 宁可多问一次，不可静默出错 |

**原则**：**冲突宁可可见，不可静默。** 一个被静默丢弃的日程比一个弹出来的冲突提示危险得多。

## 八、本地存储布局

```
<appdata>/
├── oplog/          # 追加写；唯一真相来源
├── snapshots/      # 定期折叠结果；可丢弃重建
├── blobs/<hash>    # 内容寻址附件；按需拉取
├── index/          # 派生索引（向量 / 全文）；可重建
└── keys/           # 密钥；优先放 OS 钥匙串而非此处
```

**约定**

- `oplog/` 是唯一真相来源，丢失不可恢复
- `snapshots/` 与 `index/` 属于派生态，**任何时候都可以删除并重建**
- `blobs/` 按内容哈希命名，同内容只存一份

## 九、对 pi-durable 的关系

pi-durable 提供**事务化持久化**（会话、任务、文档先落盘再展示，崩溃可续跑），这对 agent 执行状态非常有用，**应当复用**。

但它的文档明确写着：

> One process owns a storage at a time; there is no cross-process locking.

因此：

| 用途 | 是否用 pi-durable |
| --- | --- |
| agent 执行状态、会话记录 | ✅ 用，但**必须包一层自有抽象**（它是 Experimental） |
| 用户数据（笔记、日程）的同步 | ❌ 不用它的同步语义；同步走本项目自己的 op log + CRDT |
| 多设备共享同一存储 | ❌ **绝对不可以** |

**写权必须由本项目的协调层串行化**（租约），不能指望底层存储。

## 十、同步前沿、因果上下文与压缩

这一节是 2026-10-14 新增的（[ADR-0015](./decisions/0015-sync-frontier-and-compaction.md)），
一次性关掉了 [open-questions](./open-questions.md) 的 #13、#14、#15。三者其实是同一个问题：
**「这台设备到底确凿收到了哪些操作？」**

### 10.1 同步前沿 = 连续前缀

`Frontier` = 设备 id → HLC，含义被**限定**为：

> `frontier[source] = h` ⟺ 我收到了 `source` 产生的、**HLC ≤ h 的全部**操作。

**它不是「我见过 source 的最大 HLC」。** 后者中间可以有洞（先收到 h3、错过 h2，
最大值停在 h3 而 h2 缺失），拿它当安全判据会让离线设备重连后复活已删除的数据。
因此两者在代码里**分开命名**：`advanceFromClaim` 是连续前缀，`latestSeenPerSource`
是「见过」—— 后者**只许用于展示与调试**。

前沿只能靠两条**可证明**的路径推进：

| 路径 | 证明什么 |
| --- | --- |
| 对端的 `SourceClaim`（`count` + `head`） | 手中该来源操作去重后条数 = `count`，**且**最大 HLC 恰好 = `head`。两个条件缺一不可：只比条数会被过期声明骗过，只比 `head` 排除不了中间的洞 |
| 采纳快照 | 快照本身就是「前沿之前的全部操作已折叠」的证书 |

### 10.2 因果上下文

每条新操作应当带上 `causalContext`（见第三节）。写入路径不盖章，
`areConcurrent` 就只能返回「不可判定」—— 冲突检测会如实报告这一情况，而不是猜。

### 10.3 快照与压缩

```
       已压缩区间                        未压缩尾部
  ├──────────────────────┤├──────────────────────────────┤
   由「前沿」负责                  由「完整 opId 摘要」负责
   （可证明的连续前缀）              （无条件正确，且现在是有界的）
```

- **安全水位** = 所有配对设备都已确认的前沿 = 逐来源取最小值。
  **只要有一台设备没上报，水位为空，什么都不可压缩。**
- 它与第四节的墓碑裁剪前置条件**是同一个谓词** —— 所以「压缩不能与墓碑裁剪打架」
  是构造上成立的，不靠纪律。
- **先折叠成快照，再删日志。** 顺序颠倒会在任何一次失败后造成不可恢复的数据丢失
  （`oplog/` 是唯一真相来源）。
- 被 pin 住的墓碑必须用 `retain` 保住。它的效果已经在快照里，因此本地重建
  **只折叠前沿之上的尾部**，不能折叠整个日志。
- 快照携带 `schemaVersion`，采纳时经第五节的迁移链迁移。

### 10.4 冲突的位置

冲突报告的位置用 **RFC 6901 JSON Pointer**（`""` 表示整个实体），而不是字段名 ——
因为嵌套字段（`/attendees/0/email`）必须能表达。「哪个操作写哪个路径」由实体模型提供，
core-sync 不猜。

## 十一、检查清单

写任何碰数据的代码之前，确认：

- [ ] 用 ULID 而非自增主键
- [ ] 变更表达为 op，而非直接改字段
- [ ] 携带 HLC，而非裸墙钟
- [ ] 删除写墓碑，而非物理删除
- [ ] 实体带 schemaVersion，迁移是纯函数
- [ ] 判断过这份数据属于「可合并 / 可重建 / 内容」哪一类
- [ ] 冲突规则明确，且不会静默丢弃数据
- [ ] 没有让两台设备同时写同一份存储
- [ ] 判断「对端收到了什么」时用的是**同步前沿**，而不是「最新 HLC」（两者不是一回事）
- [ ] 压缩日志前先折叠成快照，安全水位由**所有配对设备**的前沿取最小值得出
- [ ] 写入路径给 op 盖了 `causalContext`，否则冲突永远判不出来
