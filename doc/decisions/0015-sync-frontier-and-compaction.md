# ADR-0015：同步前沿（sync frontier）作为裁剪、压缩与冲突判定的共同原语

- **Status**: Accepted
- **Date**: 2026-10-14
- **Supersedes**: —

## Context

`open-questions` 里有三个问题一直悬着，而且它们都写着同一句话：**「必须与 `core-mesh` 一起设计」**。

| 问题 | 表面上的诉求 |
| --- | --- |
| #15 | 裁剪水位不能是「最新 HLC」，应该是「同步前沿」 |
| #13 | `OpLog` 缺少快照与压缩能力，但压缩不能削弱「对端还缺哪些操作」的判断 |
| #14 | 没有任何类型能表达「两个并发写入冲突了」 |

复核之后可以确认：**这不是三个问题，而是同一个缺失的原语从三个方向暴露出来。** 三者真正要回答的都是：

> **这台设备到底**确凿**收到了哪些操作？**

- #15 要它来判断「这条墓碑能不能丢」
- #13 要它来判断「这段日志能不能压缩」
- #14 要它来判断「这两条操作是不是互相没见过」

而且三者都受同一个约束支配：**「最新 HLC」这种「见过」的语义不够用。** 一台设备先收到 h3、错过 h2，最大值就停在 h3，而 h2 缺失。#15 里的复活路径、#13 里「水位漏数据」的顾虑，根因都是把「见过」当成了「收全了」。

因此继续分别处理这三件事，会得到三套半对的机制；一起处理，只需要一个类型。

## Decision

引入**同步前沿（Frontier）**作为唯一的因果摘要原语，三处共用。

### 一、原语：连续前缀，且只有两条推进路径

`frontier[source] = h` 的含义被**限定**为：**我收到了 `source` 产生的、HLC ≤ h 的全部操作**。

关键词是**连续**。它与「见过 source 的最大 HLC」是两个不同的概念，因此代码里也刻意分成两个名字：

| 函数 | 语义 | 能否作为安全判据 |
| --- | --- | --- |
| `advanceFromClaim` / 快照采纳 | 连续前缀 | ✅ |
| `latestSeenPerSource` | 见过的最大值 | ❌ 只用于展示与调试 |

前沿只能通过**可证明**的两条路径推进：

1. **批量证明**（`advanceFromClaim`）：来源设备声明「我共有 `count` 条操作，最后一条是 `head`」。接收方必须**同时**满足「持有的该来源操作去重后条数 = `count`」与「持有的最大 HLC 恰好 = `head`」才推进。
   - 只比条数会被**过期声明**骗过：手里是 {1..11, 15}，条数同为 12，中间却有洞。
   - 只比 `head` 无法排除中间有洞。
   - 两者同时成立时，条数为 12 且最大值为第 12 条的集合**只可能是 {1..12}**（opId 唯一），于是推进是安全的。
2. **采纳快照**：快照本身就是「前沿之前的全部操作已折叠」的证书，采纳它即把前沿推进到快照前沿。这也是压缩之后补齐历史数据的唯一路径。

刻意**没有**选择的路：给 `Op` 加一个按设备稠密的序号（`seq`）。它同样能证明连续性，但那是对 data-model.md 第三节 `Op` 结构的侵入式修改，而「条数 + head」用的是既有字段，证明强度相同。

### 二、#15 修复：裁剪需要两个互不替代的条件

`PruneWatermark` 的输入从「每台设备的最新 HLC」改为「每台设备上报的前沿」，参数名 `latestByDevice` → `frontiersByDevice`（旧名字的歧义本身就是这个 bug 的温床）。裁剪条件变成：

| # | 条件 | 用途 | 不能替代它的东西 |
| --- | --- | --- | --- |
| 1 | 未被 pin | 彻底删除流程进行中必须保留 | — |
| 2 | 水位完整 | 有设备没上报就一律不裁剪 | — |
| 3 | 年龄 ≥ 保留期 | 用**各设备自身进度的最小值**当墙钟 | 不能用本机墙钟（PR #2 已修） |
| 4 | **每台配对设备的前沿都覆盖该墓碑** | 确认它**真的收到了这一条** | **不能用条件 3 代替** |

条件 4 是本次修复的核心。反例（已在测试中固定下来）：A 删除笔记 N 产生墓碑 T，此后 A 与 B 再没成功同步过、但各自持续本地写入；180 天后两端的最新 HLC 都远超 T，条件 3 放行 —— 于是 A 裁掉 T，B 重连后 N 复活。用前沿判定时，B 的前沿里根本没有 A 的 T，条件 4 拒绝放行，同时 `isTombstoneAtRisk` 如实报警，UI 得以显示「N 台设备尚未确认」而不是「已彻底删除」。

### 三、#13 解决：压缩与对账的分段契约

**压缩水位 = 所有配对设备都已确认的前沿 = 逐来源取最小值。** 这与条件 4 是**同一个谓词**，「不能与墓碑裁剪打架」这条约束因此是构造上成立的，而不是靠约定。

对账随之分成两段，各有各的正确依据：

```
       已压缩区间                        未压缩尾部
  ├──────────────────────┤├──────────────────────────────┤
   由「前沿」负责                  由「完整 opId 摘要」负责
   （可证明的连续前缀）              （无条件正确，且现在是有界的）
```

- **前沿之下**：压缩的**前提**就是每台设备都已收全这一段，所以「对端缺这一段」这个判断根本不会出现 —— 这不是近似，而是压缩的定义。对端若真的落后（新配对、前沿为空），走**快照**补齐（`coverageGap` 判定何时退化）。
- **前沿之上**：这一段没有压缩，`opsMissingFrom` 的完整摘要照旧适用，丢包与乱序都不会漏数据。

于是 #13 最难的第四条（「必须保住『对端还缺哪些操作』的判断能力」）得到满足：**摘要只跑在有界的尾部，而尾部之下的判断由可证明的前沿承担。** 附带一个很好的性质：对端在中间漏了一条，它的前沿只能停在洞之前，因此**洞之后的所有操作都不会被压缩掉**。

快照携带 `frontier` 而不是某个时刻，并带 `schemaVersion`：采纳时经 `MigrationRegistry` 迁移，满足 #13 第五条（快照同样受 schema 版本化约束）。

### 四、#14 解决：冲突可见需要因果上下文

`Op` 增加一个**可选**字段：

```
causalContext?: Frontier   // 产生这条操作之前，本设备已知的前沿
```

理由：HLC 给的是**全序**，全序不等于因果序。A 在 wall=100 写入、B 在 wall=101 写入，二者可能并发、也可能 B 见过 A —— 只比时间戳区分不了（`wall` 前进时 `counter` 归零，反而抹掉了「见过」的痕迹）。有了 `causalContext`，`areConcurrent` 才是可判定的。

在此基础上给出冲突的**形状**，解决策略完全留给实体模型：

| 字段 | 含义 |
| --- | --- |
| `entityId` + `path` | 冲突发生在哪里。`path` 用 RFC 6901 JSON Pointer（`""` 表示整个实体） |
| `opIds` | 参与冲突的操作，按全序排列 |
| `resolution` | `auto`（已由自动策略解决）/ `manual`（必须由人选） |

`resolution: "auto"` **不免除呈现义务** —— ADR-0012 的要求是冲突宁可可见，UI 仍应让用户知道「这里发生过并发写入」。

位置寻址选 JSON Pointer 而非字段名，是因为嵌套字段（`/attendees/0/email`）必须能表达；而「哪个操作写哪个路径」只有实体模型知道，所以由调用方提供 `pathOf`。

**三态判定**：`areConcurrent` 返回 `boolean | undefined`。缺因果上下文时返回 `undefined`（不可判定），而不是 `false`。把「不知道」当成「没有冲突」会让冲突静默消失，那正是本决策要消除的失败模式；`detectConflicts` 因此额外返回 `undecidable` 计数，让「有 reducer 没盖章」成为一个可观测信号。

## Consequences

**正面**

- 三个悬置问题一次性关闭，且共用同一个可测试的原语，不存在三套互相打架的机制
- 裁剪与压缩共用同一个安全谓词，**「不能与墓碑裁剪打架」由构造保证**，不再依赖实现者的纪律
- 对账带宽从 O(全部日志) 降到 O(尾部)：既是性能收益，也让压缩后的正确性论证更容易（尾部的判断本来就是无条件正确的）
- 冲突类型有生产者（`detectConflicts`）、有消费者（UI），不是死类型；且「不可判定」被显式暴露而不是被吞掉
- 前沿是**可序列化的普通对象**（不是 `Map`），可以直接作为协议字段传输

**负面**

- **`Op` 结构被修改**（新增可选的 `causalContext`）。这是 data-model.md 第三节「第一天必须做对」的契约，属于侵入式变更。虽然字段可选、旧数据仍可解析，但**必须由 `core-mesh` 在写入路径上盖章**，否则 #14 的判定永远退回「不可判定」。
- **多了一份需要持久化与传播的状态**：每台设备要维护并上报自己的前沿。它比「一个 HLC」复杂，且前沿表随设备数增长。
- **前推进依赖声明，声明不实时**。过期声明不会导致错误推进（两条校验都会拦下），但会让压缩水位**偏保守** —— 表现为「空间回收比预期慢」，需要可观测性来区分「保守」与「卡死」。
- 压缩引入不可逆操作：**先折叠再删除**的顺序不能颠倒，否则那段操作既不在日志也不在快照里。这是 `oplog/` 作为唯一真相来源之后第二个需要专门测试的破坏性路径（第一个是快照裁剪墓碑，见 ADR-0014）。
- `retain` 保住的 pin 墓碑会留在日志里、同时其效果已在快照里。本地重建必须只折叠前沿之上的尾部（`restoreFromSnapshot`），这条约束的前提是折叠**可交换且幂等**（data-model.md 第七节已要求 CRDT / LWW 语义）。
- 测试策略的负担上升：这一层的性质（连续性、幂等、顺序无关）比 CRDT 合并本身更抽象，需要靠变异性用例（例如「条数凑巧相同但 head 对不上」）才钉得住，而不是靠正例。

## Alternatives considered

**给 `Op` 加按设备稠密的序号 `seq`** — 连续性的证明会更直接（`frontier = 已收到的最大连续 seq`）。被否决：收益与「条数 + head」等价，但代价是修改 `Op` 的核心结构（每个设备还要维护并持久化 `seq`）。`causalContext` 已经是一次必要的侵入，没有必要再来一次。

**保留「最新 HLC」水位，另加一份逐墓碑确认集合** — 改动面最小，条件 4 也能成立。被否决：那是一份 O(墓碑数) 的新状态，与 ADR-0013 的体积预算直接冲突，而且它解决不了 #13（压缩仍然无法判断对端缺哪些操作）。同一个原语已经能覆盖两者，没有理由再引入第二套。

**用 Merkle 树做对账** — 通信量最优（O(log n) 定位差异），是分布式同步的成熟做法。被否决（非否定）：它解决的是「找出差异」的成本，而不是「差异能不能被证明已经补齐」的问题；本决策的核心困难是后者（压缩之后如何继续证明）。Merkle 树可以作为尾部摘要的后续优化叠加进来，不影响前沿语义。

**每台设备各自维护「已确认收到」的显式 ack 台账** — 语义最直白。被否决：状态量与设备数 × 操作数同阶，且 ack 本身也要同步，等于把同一个问题复制一层。

**冲突用字段名寻址（`"title"` 而不是 `"/title"`）** — 更易读。被否决：无法表达嵌套与数组下标，而日程的参与者列表恰恰是嵌套结构。JSON Pointer 是标准且可序列化，读起来的差距可以用 UI 层补。
