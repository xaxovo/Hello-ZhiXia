# 未决问题与已知风险

标注含义：

- **P0** — 动代码之前必须有结论，否则会写错数据层或事后返工
- **P1** — 第一个可用版本之前要有结论
- **P2** — 可以边做边定

---

## P0

### 1. 提醒的「恰好一次」归属算法 → **已解决** · [ADR-0011](./decisions/0011-reminder-exactly-once.md)

**问题**：无中心 mesh 里没有天然的唯一调度者。所有节点都调度 → 收到 N 次提醒；只有一个调度而它关机 → 完全收不到。

**当前倾向**：确定性归属（当前在线的节点中 ID 最小者拥有今天所有定时任务）+ 幂等键（每条提醒带唯一 ID，重复触发直接丢弃）+ 由设备本地注册系统级闹钟而非 agent 投递。

**待定**：节点集合变化时的交接窗口怎么处理？交接瞬间的漏触发是否可接受？

**影响**：提醒是日常助手的核心功能，这个算法的数据模型必须第一天就写对。

---

### 2. 写权租约的粒度 → **已解决** · [ADR-0012](./decisions/0012-write-lease-granularity.md)

**问题**：pi-durable 无跨进程锁，多设备同写同一份存储是未定义行为。需要租约来串行化。

**待定选项**：

| 粒度 | 优点 | 缺点 |
| --- | --- | --- |
| 全局单写者 | 实现最简单，绝对安全 | 同一时刻只有一台设备能干活 |
| 会话级 | 不同会话可并行 | 会话之间仍有共享资源（知识库、日程） |
| 资源级 | 并发度最高 | 实现复杂，死锁风险 |

**建议**：先做**会话级 + 关键资源（日程库）独占**，即混合粒度。

---

### 3. 知识库的规模上限 → **已解决** · [ADR-0013](./decisions/0013-knowledge-base-scale.md)

**问题**：「全量复制结构化数据」是否可持续，取决于知识库有多大。

**待定**：笔记数量的预期量级？是否需要索引全文 PDF 与图片 OCR？如果知识库会长到几万条，全量复制的启动时间与内存占用是否可接受？

**影响**：决定是否需要把知识库本身也做成「元数据全量 + 正文按需」。

---

### 4. 墓碑保留期与「彻底清除」语义 → **已解决** · [ADR-0014](./decisions/0014-deletion-semantics.md)

**问题**：墓碑必须长期保留，否则离线设备会复活已删除数据。但「长期」是多久？用户要求「彻底删除我的数据」时，能不能做到？

**待定**：

- 墓碑保留期下限 = 「设备可能离线的最长时间」，这个值怎么定？
- 「彻底清除」是否需要所有设备在线确认？还是接受「最后一致」并如实告知用户？

### 9. 三端同步的测试策略 → **已解决** · `@hzx/core-sync/sim`

**问题**：同步与冲突逻辑最容易出错，而它恰恰最难测 —— 需要模拟多设备、网络分区、时钟偏移、离线重连。

**为什么是 P0**：[ADR-0010](./decisions/0010-delivery-strategy.md) 确定「各端先跑通、互联最后做」，其最大代价正是**同步问题的反馈周期很长**。若没有确定性模拟器，网络分区与时钟偏移类 bug 几乎不可能手工复现，只能在上线后暴露。

**结论**：已实现**确定性多节点模拟器**（`@hzx/core-sync/sim`）——同一进程内跑多个虚拟设备，可注入分区、丢包、乱序、时钟偏移；相同种子必然得到同一份 trace，失败的用例可以精确重放。

**选型结论**：采用**进程内虚拟节点**，而非「多进程 + 可控网络代理」。理由是这一层的目标是让同步与合并逻辑可单元测试，速度与可复现性优先；多进程方案的价值在于验证真实的序列化与传输实现，那属于集成测试，不是这一层要解决的问题。不引入现成网络模拟工具，同样是为了避免把「确定性」交给外部依赖。

**已覆盖的性质**：双向对账补齐、双方各自离线写入后互相同步、三方分区、持续 50% 丢包、丢包叠加乱序、时钟偏移 10 分钟、接收后本机 HLC 的因果序、同种子轨迹一致、重复投递幂等。

> ⚠️ **一条方法论记录，值得团队记住**：模拟器写完后做了一次变异测试 —— 把 anti-entropy 的应答改成「没有缺失就不回复」。结果 **18 个用例全部照常通过**，说明它们没有真正钉住这个行为。
>
> 原因是有隐蔽性的：只要**两侧都会主动发起对账**，方向性由发起方轮转保证，单向应答照样收敛。缺陷只在「只响应、不主动发起」的设备上才暴露 —— 而那正是 ADR-0006 里 Android 瘦客户端的形态。
>
> 补了一个对应的用例后，变异才被精确捕获（19 个用例中恰好 1 个失败）。教训：**分区与收敛类测试极易写成空转**，因为它们验证的是「最终一致」这个弱性质，而错误的实现往往也能最终一致。写完这类测试后应当做一次变异，确认它真的会红。

### 13. `OpLog` 缺少快照 / 压缩能力 → **P0（新增）**

> 来自外部代码审查（公开仓库 PR #5），**不是原始文档中的条目**。经复核成立，故收录。

**问题**：`OpLog` 接口只有 `append` / `all` / `since` / `has` / `size`，全仓库只有一个内存实现 `createMemoryOpLog`，其注释自己写着「生产环境应换成持久化实现」。日志**只追加、不收缩**。

**为什么必然会撞上**（不是「可能」，是「一定」）：

- ADR-0013 存在体积预算，而墓碑保留期就直接受它约束
- `all()` 与 `since()` 每次都对全部操作排序；anti-entropy 的完整摘要带宽是 O(n)
- 每台设备持有**全量副本**，而个人助手是要常年运行的 —— 日志增长没有上限

**任何方案都必须满足的约束**（从既有决策推出，不是偏好）：

1. **幂等**：同一条操作重复投递不产生副作用（`op.ts` 的合并契约）
2. **与到达顺序无关**：合并结果只取决于最终收到了哪些操作
3. **不能与墓碑裁剪打架**：被 pin 住的墓碑不能丢（`deletion.ts`）
4. **必须保住「对端还缺哪些操作」的判断能力** —— 这是真正的难点。`opsMissingFrom` 刻意用**完整 opId 摘要**而不是「最大 HLC 水位」，因为水位在丢包与乱序下会漏数据（设备先收到 h3、错过 h2，水位停在 h3，h2 就永远补不回来）。压缩掉操作之后如何继续满足这条，是整个设计的核心。
5. **快照自身也受 schema 版本化约束**：迁移是纯函数，且迁移链必须从任意历史版本可达（`schema.ts`）

**为什么现在不写接口**：压缩之后的对账语义**直接决定 `core-mesh` 同步协议的形态**，而 ADR-0010 把「互联」放在最后做。在这里先定接口等于反过来把协议设计锁死。**必须与 `core-mesh` 一起设计。**

## P1

### 5. rendezvous / relay 的部署与成本模型

**问题**：默认公共节点由我们运营，带宽与可用性都是我们的成本与责任。

**待定**：节点部署在哪、几台、中继流量占比预估多少、是否需要限速、自托管切换的配置形态。

---

### 6. 附件按需拉的离线降级

**问题**：用户在地铁上打开一篇引用了附件 PDF 的笔记，附件没拉到本地。

**待定**：显示占位与重试？还是提前按规则预取（最近 N 天用过的）？预取规则如何不浪费移动流量？

---

### 7. 权限门的粒度

**问题**：pi 没有内置权限系统，权限门必须自建。粒度太粗不好用，太细会烦人。

**待定**：

- 按工具授权（「允许发送邮件」）还是按副作用类别（「允许对外发送任何内容」）？
- 是否需要「本次会话内允许」这样的临时授权？
- 首次授权如何在三端之间同步（Android 上没有算力节点时能否授权）？

---

### 8. 提示注入的缓解措施

**问题**：agent 同时具备「读私密数据」与「对外发请求」两种能力时，风险是**相乘**的。一封邮件里的恶意指令可以让 agent 把笔记外发。

**待定方向**：

| 手段 | 效果 | 代价 |
| --- | --- | --- |
| 出站白名单（只允许访问用户显式批准的目标） | 强 | 可用性下降 |
| 所有出站副作用人工确认 | 强 | 烦人，用户会习惯性点同意 |
| 私密数据与出站能力物理隔离（不同 agent 实例） | 强 | 架构复杂 |
| 内容标记与来源追踪 | 弱但便宜 | 不能单独依靠 |

**建议**：出站白名单作为默认，人工确认作为白名单之外的兜底。

### 14. 没有任何冲突表达类型 → **P1（新增）**

> 同样来自 PR #5 的代码审查，**不是原始文档中的条目**。

**问题**：`op.ts` 提供了 `Reducer` 与 `foldOps` 两个插槽，但仓库里**没有任何实体 reducer**，也没有任何类型能表达「两个并发写入冲突了」。

**为什么需要**：ADR-0012 与 `ui-shared` 的要求是明确的 —— **冲突宁可可见、不可静默**，日程时间与金额这类数据的冲突必须呈现在 UI 上，而不是被 LWW 悄悄覆盖。没有冲突类型，UI 层就无从呈现。**这条要求目前只写在注释里，没有任何类型支撑。**

**为什么现在不写接口**：冲突的**形状**取决于实体模型（哪些字段可以 LWW、哪些应该取并集、哪些必须交给人选），而实体模型目前完全不存在（连一个 reducer 都没有）。此时定下 `Conflict` 类型，会得到一个既没有生产者、也没有消费者的死类型。

**可以先做的部分**：若希望先有接口，可以只定「冲突发生的位置 + 参与冲突的操作 + 是否已自动解决」这三样，把**解决策略**完全留给实体自己决定。但连「位置」用什么寻址（字段名 / 路径 / JSON Pointer）都取决于实体模型。

### 15. 裁剪水位需要的是「同步前沿」，不是「最新 HLC」 → **已解决** · [ADR-0015](./decisions/0015-sync-frontier-and-compaction.md)

> 来源：对已合并 PR #2 的复核。方向正确，但模型仍有一个洞。

**背景**：PR #2 把 `isTombstonePrunable` 从「本机墙钟」改为「跨设备安全水位」（`PruneWatermark`），方向是对的 —— 原来的实现让一台时钟快 180 天的设备能提前裁剪**刚创建**的墓碑，那会导致离线设备重连后复活已删除数据（已在未修复代码上直接复现）。

**残留的问题**：目前的水位是**每台设备一个最新 HLC，取最小值**。但一台设备的「最新 HLC」只反映它自己的时钟与本地写入，**不能证明它收到了某条特定的墓碑**。设想：

1. A 删除笔记 N，产生墓碑 T（HLC 为 `t`）
2. 此后 A 与 B **再没有成功同步过**，但两台设备都各自在本地持续写入
3. 180 天后，A 与 B 各自的最新 HLC 都远超 `t`
4. 水位判定为「完整且已越过保留期」→ A 裁剪掉 T
5. B 终于重新连上 —— 它本地那份 N 还在（因为它从未收到删除）→ **N 被复活**

**正确的原语**：水位应当是每台设备报告的**同步前沿** —— 对每一个来源设备，我收到了它到哪个 HLC 为止的全部操作。判定某条墓碑能否裁剪的条件是：**对所有设备 d，`frontier_d[墓碑来源] ≥ 墓碑的 HLC`**。

**结论**：残留的问题已按上面「正确的原语」修复。

| 改动 | 内容 |
| --- | --- |
| 水位输入 | 从「每台设备的最新 HLC」改为「每台设备上报的**同步前沿**」（`frontier.ts` 的连续前缀） |
| 参数改名 | `latestByDevice` → `frontiersByDevice` —— 旧名字的歧义正是这个 bug 的温床 |
| 裁剪条件 | 增加第 4 条：**每台配对设备的前沿都必须覆盖该墓碑**（`tombstoneConfirmed`）。它与「保留期已过」**互不替代** |
| 保留期墙钟 | 仍取「各设备自身进度的最小值」，但它的职责被限定为**只用于保留期**，不再冒充收到确认 |
| 风险提示 | `isTombstoneAtRisk` 现在也覆盖「水位完整、但某台设备的前沿没覆盖这条墓碑」—— 正是上面第 5 步那台设备 |

上面那段复活路径已经作为回归用例固定下来：`deletion.test.ts` 的「某台设备从未收到墓碑时，即使所有设备的最新 HLC 都远超它，也不可裁剪」（并断言旧判据会放行，以证明这条用例不是在空转）。

原判断「应该与 #13、`core-mesh` 一起解决」完全正确 —— 两者确实共用同一个谓词（见 #13 与 ADR-0015）。

## P2

### 10. 成本熔断的阈值与实现

**问题**：多设备 + 后台任务 + 主动触发，LLM 费用可能失控。pi 提供事后 usage 统计，但需要的是事前熔断。

**待定**：按天/按月的额度、超限行为（拒绝执行 / 降级到本地模型 / 仅提醒）、embedding 重建的单独预算。

---

### 11. Android 分发的具体形态

**问题**：Android 不做瘦客户端以外的选择已定，但分发方式未定。

**待定**：APK 侧载（会有系统安全警告）还是上架应用商店（需要隐私政策，且 P2P 类应用可能被质疑）。自建安装包 + 应用内更新的方案在 Android 上需要额外处理「允许安装未知来源」。

---

### 12. 诊断与遥测

**问题**：无中心服务器意味着没有崩溃上报。但用户遇到问题时，没有日志几乎无法排查。

**待定**：默认全关、用户主动导出诊断包？还是默认开启匿名崩溃上报（需要服务端）？

**倾向**：默认全关，提供「一键导出诊断包」，由用户自行发送。

## 已知风险（非待决，持续监控）

| 风险 | 说明 |
| --- | --- |
| pi-durable 处于 Experimental | API 可能破坏性变更；已有抽象层隔离，但升级仍需人工验证 |
| 见面点单点故障 | 公共节点挂掉时，跨网设备无法建立连接（同局域网不受影响） |
| 提示注入 | 无法根除，只能缓解；需持续跟踪业界进展 |
| 全量复制的长期可持续性 | 已定降级阈值，见 [ADR-0013](./decisions/0013-knowledge-base-scale.md) |
